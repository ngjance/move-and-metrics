# Move & Metrics

A coach-analyst toolkit for preventive health and wellness. It turns activity data into
decisions a coach can act on, and (in layer 2) shows how an AI agent can help a trainer prepare
client check-ins safely, with a human approving every message.

**Author:** Ng Li Juan (Jance Ng), data analyst and certified personal trainer.

> All data in this repo is public or synthetic. No real client data is used or stored.
> Outputs are informational coaching aids, not medical advice.

## Two layers

| Layer | What it is | Status |
|---|---|---|
| **1. Analytics** (`layer1_analytics/`) | Coach dashboard (piece 1) and early-warning churn model with explanations (piece 3) | Scaffolded and tested |
| **2. Coach Copilot** (`layer2_copilot/`) | AI agent that uses layer 1 as tools to draft weekly client check-in briefs; loop, guardrails and test harness | Design only, to build next |

Layer 2 reads from layer 1: the dashboard supplies trends and status, the model supplies a risk score.

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m unittest discover tests -v                    # checks everything works
python -m layer1_analytics.pt_generate                  # build the synthetic personal-training database
python -m layer1_analytics.pt_risk                      # train the renewal model and score open packages
python -m layer1_analytics.pt_analysis                  # what is associated with not renewing? (report in docs/analysis)
streamlit run layer1_analytics/dashboard.py             # renewal-risk dashboard
```

To use real public data, see [`data/README.md`](data/README.md).

## Synthetic personal-training database

`data/synthetic/` holds a linked, **made-up** personal-training database (35 clients, 53 packages,
about 2,900 session records), generated by `python -m layer1_analytics.pt_generate` with every setting
in `layer1_analytics/pt_config.py`. It includes planted cases such as a prenatal client who pauses with
10 sessions left, returns postpartum, finishes, and does not renew (recorded as a pause, not a drop-off).
`personal_training_synthetic.xlsx` shows the same data with live formulas for sessions left, package used %,
pace excluding pauses and more. See `docs/synthetic_assumptions.md` for what was assumed.

## Layer 1 details

- **Dashboard (`dashboard.py`), two tabs.**
  *Renewal risk:* for each package with sessions left, a model-estimated chance of not renewing, the main drivers in plain
  English, package used, sessions left, days since the last session and pace vs plan. Maternity pauses show as life stage, not churn.
  *What predicts non-renewal?:* the association results below.
- **Renewal model (`pt_risk.py`):** logistic regression **learned from past packages** (no hand-set rules), using only
  information available when half the package was used (no look-ahead): gym attendance (cancels, no-shows, pace, gaps) plus
  **activity outside the gym over the most recent 30 days** (steps, active minutes, days with Fitbit data, step trend).
  The 30-day window matches the length of the Fitbit file. Adding the activity inputs improved cross-validated AUC only
  slightly (0.735 to 0.749, within the noise). Trained on 10 other synthetic cohorts and scored on the
  35-client cohort, which is held out. Grouped cross-validation AUC is about 0.73.
- **Association analysis (`pt_analysis.py`):** tests whether skipped sessions, pause length, activity outside the gym and body measures
  (body weight, body fat %, skeletal muscle mass) go with not renewing,
  with confidence intervals (resampling whole clients), Holm correction for multiple tests, dose-response tables and charts, an adjusted
  model, and a check that the method finds a planted effect and does not invent one. Output: `docs/analysis/report.md`.
- **No expiry dates and no lapse rule.** A package stays open until its sessions are used up. A client who stops attending stays Active
  and never gets an outcome, so such clients are not in the training or analysis data. In real use, record a closure status.
- **Fitbit-only dashboard (`dashboard_fitbit.py`):** the first version, activity only, no packages.
- **Generic churn model (`churn_model.py`):** runs on the optional Kaggle gym churn file or `--demo`.

Run order: `pt_generate` (data) -> `pt_risk` (train, write `data/synthetic/renewal_risk.csv`) -> `pt_analysis` (report and charts; add `--validate` for the planted-effect test) -> `streamlit run layer1_analytics/dashboard.py`.

## Limitations (read before quoting any result)

- The Fitbit data is old (2016) and small (30 users, about a month). Patterns are illustrative. Attached to made-up clients with `--fitbit`, it has no real link to their bookings, so it only shows the plumbing works.
- The gym churn dataset is described as hypothetical, so the model shows a method, not real-world churn drivers.
- The two Kaggle datasets are not linked to each other. The synthetic PT database is the linked one, but it is made up: models trained on it show a method, not real findings.
- Fitbit zero-step days may mean the tracker was not worn rather than no activity.
- Associations are not causation.
